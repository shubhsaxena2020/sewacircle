# SewaCircle v2 — adversarial strategy review

19 November 2026. UC16 is fixed. **FACT** means an opened primary page or a checked repository artifact; **INFERENCE** is a conclusion from those facts; **OPINION** is a strategic judgment. `NOT FOUND` never means the feature does not exist. Product comparisons cover public descriptions, not authenticated organiser screens.

## Verdict on the owner's doubt

**OPINION: the doubt is justified.** SewaCircle is not shown to be a *code* copy of MY Bharat, but much of v1 is a functional duplicate: discovery/matching, skills and location filters, attendance, recognition, records, WhatsApp access and an impact dashboard are already described by MY Bharat or other platforms. The current distinctive combination is **reviewed bilingual task parsing + constraint-based, dropout-tested role allocation + a visible explanation of unmet roles**. Host-reviewed evidence helps complete UC16; a hash chain alone is neither unique nor proof of work. The v1 pitch should be cut to a mission-assurance workflow, not expanded into another youth platform. [MY Bharat about](https://mybharat.gov.in/about_mybharat), [PIB volunteer-management factsheet](https://www.pib.gov.in/FactsheetDetails.aspx?Id=150695&lang=10&reg=23), [PIB MY Bharat monitoring reply](https://www.pib.gov.in/PressReleseDetailm.aspx?PRID=2222299&lang=1&reg=6).

**OPINION: v1 is not yet a credible top-five claim.** The [official judging criteria](https://www.inmobi.com/ai-kaushal) reward approach novelty, a working build, measured outcome, deployment and built safeguards. Our strongest result is on an author-generated synthetic fixture, and the careful manual baseline ties our dropout metric. v2 can become a contender if independent task cases and an organiser-observed workflow validate the gap; the rank against unknown teams across 17 use cases is **UNVERIFIED**.

## Judge, rival and IAS-officer attack list

1. **Problem ownership — INFERENCE:** v1 assumes an organiser manually forms teams; no interview or time-and-motion observation confirms the pain or current workflow. Ask an NSS/NYKS/NGO organiser to walk through one past drive without collecting personal records.
2. **Overlap — FACT:** MY Bharat and iVolunteer already cover much of the youth-to-record path (table above). A rival can add a solver to an existing volunteer manager. Our defence must be hard-case evaluation and a clean adapter story, not a list of features.
3. **Novelty proof — NOT FOUND:** no authenticated MY Bharat organiser view or procurement spec was inspected. Say exactly what public pages did and did not reveal.
4. **Impact wording — FACT:** MY Bharat already says “impact tracking”; SewaCircle currently has no independently observed community outcome. Distinguish *coverage/attendance/host-attested output* from social impact or causal benefit.
5. **Synthetic data shaped for the algorithm — FACT:** `backend/app/data/synth.py` deliberately makes some skills scarce and calls `_ensure_feasible`; it draws availability, history and ages by hand. This can make standby optimisation look useful by construction. Preserve the generator, then test separately on independently written cases.
6. **Trivial coverage — FACT:** the rerun of `python -m eval.harness` on 19 Nov gives role coverage **0.917 for CP-SAT, nearest-skill and manual-greedy**. Never claim coverage improvement against those two.
7. **Baseline asymmetry — FACT:** nearest-skill holds no standby, while manual-greedy does. CP-SAT dropout robustness **0.760 vs 0.153** nearest-skill, but **0.760 vs 0.760** manual-greedy. Present both; a human with a backup may already solve this part.
8. **Fairness overclaim — FACT:** repeat-pick share **0.230 vs 0.427** manual-greedy on synthetic histories, but a lower value does not establish equitable access; qualification, travel, preferences and historical exclusion matter. The same harness lists six misses, including unfilled roles. Expose denominators and infeasible tasks.
9. **Confidence intervals — INFERENCE:** paired task bootstrap over only ten authored tasks describes variability *within that fixture*, not field uncertainty. Do not say “statistically significant” or project it to UP.
10. **Extraction score leakage — FACT:** `backend/eval/extraction/briefs.json` contains 30 author-written briefs with explicit counts; the cached Claude result is 30/30, median 0 seconds. `backend/eval/extraction/run.py` greedily matches roles by skill overlap and tolerates count error of ±1 in one score. A live ambiguous dialect brief can fail. Freeze independent semantic twins, negations, implicit counts and out-of-taxonomy cases.
11. **Self-declared skills — FACT:** the solver can use them with a flag (`backend/app/solver/baselines.py`); “first-aid qualified” must not follow from a self-declared tag. Gate safety-critical roles on separately checked qualifications or leave them unfilled.
12. **Evidence trust — FACT:** `backend/app/main.py` takes an arbitrary `actor` label; the prototype has no host authentication. A confirmed card is host-*labelled*, not independently verified. Hash chaining detects some changes, not false input or coordinated file replacement (`backend/app/evidence/ledger.py`).
13. **Privacy — FACT:** `backend/app/llm/redact.py` has bounded pattern redaction; names and indirect identifiers may pass. Real youth profiles, notes and photos cannot be fed to cloud models under the prototype assumptions. The [DPDP Act](https://www.meity.gov.in/static/uploads/2024/06/2bf1f0e9f04e6fb4f8fef35e82c42aa5.pdf?v=20260911235451) and [Rules](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf?v=20261110123627) make children's data a serious deployment issue; use adults and synthetic data in the demo.
14. **Operational state — FACT:** local card JSON and ledger are file-backed, but no identity/roles, multi-user transaction model or recovery guarantee is established. The current UI is a useful prototype, not departmental software.
15. **Live-demo dependency — FACT:** LLM calls depend on a gateway; replay/cache can make a demo work but does not prove a fresh call or real latency. A cold, unseen prompt and a visible manual fallback are needed.
16. **Scale/cost — NOT FOUND:** no measured throughput, model spend per mission, data-sharing approval, uptime or staff ownership. Pilot proposal must name all of these as gates.
17. **Submission answers — FACT:** `submission/answers_v2.py` still says role coverage is the comparison and implies an export-first pilot is ready. Q2 sells the ledger as unique; Q4 omits the genuinely hard dropout preflight; Q5 promises roster time without a measured manual-time baseline. Replace with `IDEA-ANSWERS-v3.md`.
18. **24-hour originality — NOT FOUND:** the [event page](https://www.inmobi.com/ai-kaushal) says build/refine an MVP during 8–9 Dec but does not explicitly settle prior-code reuse. Document the repository and dependencies, obtain written organiser clarification, and make a smaller from-scratch branch. The owner's age 17 creates a separate eligibility/consent question; the public FAQ lists student ID but no clear minor rule in the text reviewed.

**Decision gate:** keep UC16 and pitch v2 only if the team can (a) show one end-to-end organiser decision, (b) compare with a *backup-aware* manual baseline on independent cases, (c) demonstrate a failed/infeasible case, and (d) state that no government integration or real-person verification occurred. If not, submit a narrower, honestly labelled prototype rather than claiming top-five readiness.
