**FACT — What an append-only Merkle log is stated to prove.** RFC 6962 (IETF, June 2013, opened https://www.rfc-editor.org/rfc/rfc6962.html) says logs are "publicly auditable, append-only, untrusted logs" and "The logs do not themselves prevent misissue, but they ensure that interested parties ... can detect such misissuance." §2.1.1: "If the root computed from the audit path matches the true root, then the audit path is proof that the leaf exists in the tree." We use this only as the standard design analogy: inclusion/consistency proofs establish that a recorded byte-string was in a tree, not that the real-world event it describes happened.

**INFERENCE — volunteer-hour fraud patterns and rule checks (our design, not a sourced claim).** (a) Duplicate entries: exact replay of the same payload hash, or same (volunteer pseudonym, task id, role, date) with different hours; check both exact hash equality and a near-duplicate key. (b) Impossible time overlap: one volunteer assigned to two roles with overlapping half-open intervals; `activityEndDate <= activityStartDate`; claimed hours greater than the elapsed window; unnormalised IST/UTC timestamps used to hide an overlap. (c) Host self-confirmation: `host_id == subject_id`, or host and subject sharing a pseudonym/device/contact; a single person both drafts and confirms. (d) Inflated totals: hours exceeding the event's published duration or the roster's assigned slot. (e) Ledger manipulation: rewriting an earlier entry, deleting an entry, or reordering entries — detectable by re-hashing; rolling back to a shorter chain and re-anchoring a new head is not detectable from the chain alone (needs an external witness). (f) Cross-event double counting: the same attendance evidence reused for two task ids.

## Recommendation for our build

**Implement U4 as an export of a data-model-shaped JSON, with three explicitly named modes.** `export_portable_record(mode)` where:
- `mode="ob3_dm"` → the minimal OB3-shaped example below (no `proof` field); label in UI/export metadata "Open Badges 3.0 data-model-shaped export; unsigned; not a verifiable credential".
- `mode="vc11_unsigned"` → same claims but `@context[0] = "https://www.w3.org/2018/credentials/v1"` and `issuanceDate` instead of `validFrom`; only if a consumer asks for v1.1.
- `mode="vc_signed"` → NOT in the 24-hour prototype; requires a real issuer key, a VC-JOSE-COSE or Data Integrity proof, key publication and a verifier. Do not ship a fake `proof` field.

Add `credentialSchema: [{"id": "https://purl.imsglobal.org/spec/ob/v3p0/schema/json/ob_v3p0_achievementcredential_schema.json", "type": "1EdTechJsonSchemaValidator2019"}]` only after we run a real JSON Schema validator in CI; until then declaring it would be misleading. Keep `hours` out of the OB3 field set unless expressed as text in `evidence.narrative`: there is no standard `hours` property in the classes quoted above, so inventing one without a context would be non-conformant.

**Rule checks before host confirmation (implement as pure functions returning a flag + reason string, INFERENCE design).** `dup_by_hash(payloads)`; `dup_by_key(volunteer, task, role, date)`; `overlap(intervals)` using half-open `[start, end)` after normalising to one timezone; `duration_implies(claimed_hours, elapsed)`; `self_confirmation(host_id, subject_id)`; `event_cap(hours, event_window)`; `cross_event_reuse(evidence_hash)`. Each flag must block "verified" language until a distinct host confirms; store the flag result in the ledger payload so the check itself is auditable.

**Ledger shapes (INFERENCE design).** Canonical bytes: `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")`; `entry_hash = sha256(canonical({"index": i, "prev_hash": prev, "payload": payload}))`; `prev_hash` of the first entry is 64 zeroes; `verify()` recomputes every hash and checks index/link continuity (exactly the demo above). Anchor the head hash outside the app (downloadable `.sha256` file, printed in the host's confirmation screen, or a signed timestamp in the export) so a rollback of the whole chain can be noticed. If scaling beyond a single demo, group entry hashes into a Merkle tree and publish signed roots with consistency proofs; per RFC 6962 that proves inclusion/append-only consistency of recorded leaves, not the truth of the leaf content.

**Minors and privacy (from the Act/Rules above).** Gate every flow with an age declaration; if under 18, block processing until a guardian-consent step is implemented (Rule 10's "reliable details of identity and age" or an authorised entity's virtual token; no Aadhaar number stored by us). Put an itemised, standalone notice in the UI: data items, purpose, rights, withdrawal link, complaint route (s.5 + Rules 3). Keep an append-only consent log with timestamp, notice version hash and consent string. Use pseudonymous IDs in exports; apply Rule 6-style log visibility, access control, backups and retention rather than claiming compliance. Treat the one-year retention rule as an official requirement to design for, not something this prototype has implemented.

## Risks

1. **Overclaiming U4 is the largest risk.** The OB3/VC field set is a syntax; verification, issuer accreditation and recognition are separate. A `type: ["VerifiableCredential", ...]` string without a proof is not a verifiable credential (OB3 §B.1.2 and VC1.1 §4.7 quoted above). Demo screens must render the "unsigned / synthetic" badge.
2. **Reference to MY Bharat could imply an endorsement that was not found.** Only quote their pages; do not say "MY Bharat credentials" as if we issue them.
3. **Children's data.** Under-18 volunteers are in scope of s.9; our prototype has no real guardian verification, so it must not process real minors' data. The s.9/Rule 10 regime is in the eighteen-month commencement tranche, but designing a youth product around future obligations is prudent, not proof of current compliance.
4. **Pseudonymity is not anonymity.** `urn:uuid` subject IDs plus role, date and district can be re-identifying; do not export raw names, phone, Aadhaar, PAN or precise location in the portable record.
5. **Hash-chain limits.** Anyone with write access can recompute the chain after editing; without an outside anchor, rollback/restart is invisible. A hash proves "these bytes were appended in this order", not "this person did these hours".
6. **Time semantics.** Invalid or manipulated timestamps can defeat overlap checks; all checks use canonical UTC-normalised values and must show the unparsed original for audit.
7. **Validation gap.** We checked required-field presence with stdlib only; no full JSON-LD expansion/compaction or JSON Schema validation was run (jsonschema unavailable, no installs permitted). Conformance certification is out of scope.
8. **Prototype scope.** All records are SYNTHETIC; no measured fraud reduction, no field pilot and no legal compliance determination are claimed.
