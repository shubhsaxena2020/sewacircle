## Deliverables and acceptance (tests must prove each)
1. app/data/synth.py: make_volunteers(n=40, seed=7) and make_tasks(seed=7). Deterministic. SYNTHETIC labelled. Volunteers across at least 6 UP districts with plausible coordinates (use docs/research/up_districts.json when it exists, else a small documented table and a TODO), all 24 taxonomy skills present with realistic scarcity (first aid and Awadhi speakers scarce), ages 16-35 (some minors, some with guardian_consent False to exercise the constraint), mixed gender, mixed past_drives and times_picked_last_90d (a few heavy repeat-picks). 10 labelled tasks with ground-truth RoleSpec lists: varied (water-hygiene camp, blood donation, tree plantation, literacy drive, flood relief, sports day, health camp, cleanliness drive, digital literacy, elderly care visit), different blocks and slots, some HARD (scarce skill, remote block, single first-aider) and at least 2 where the nearest-skill baseline already does well (so the eval is not rigged).
2. app/solver/metrics.py: ONE shared compute_metrics(task, volunteers, roster) used for every method, so comparisons are fair. Define precisely and document: role_coverage, slots_filled/required, robustness (for each assigned volunteer v: can every must slot still be filled from assigned-minus-v plus roster.standby using qualified, available, within-travel volunteers via bipartite matching? robustness = share of v that pass), repeat_pick_share, exposure_gini, district_spread, novices, mentor_pairs.
3. Baselines (solver/baselines.py): nearest_skill (greedy nearest volunteer having any required skill), random_feasible (seeded), manual_greedy (simulates a careful organiser: roles in order, most experienced available volunteer, plus ONE next-best backup per role as standby so the baseline gets honest credit for backups).
4. solver/cp_sat.py build_roster: OR-Tools CP-SAT. Hard constraints: availability in task.slot; qualified (skill any-of, min_level; self-declared skills allowed but flagged); within max_travel_km (haversine); minors only if guardian_consent True and task.allow_minors; one role per volunteer; forced_in/forced_out. Objective (weights documented in code): maximise must-role coverage first, then skill-fit, then proximity, then fairness (U2: penalise heavy recent picks, bonus for novices up to a cap and for novice-mentor pairs where a role needs_experienced, district spread), then resilience (U1: choose standby so any single dropout still leaves all must roles covered; maximise robustness). Every Assignment gets plain-English reasons[] (why this person: skill match, distance, availability, fairness). Time limit from options. Status reported honestly (OPTIMAL/FEASIBLE/INFEASIBLE); infeasible roles go to unfilled_role_ids, never silently dropped.
5. simulate_dropout (U1) and why_not (U3) as specified in solver/api.py docstrings, using real re-solves; narrative text must be generated from real solver deltas, not templated claims.
6. backend/eval/harness.py run_eval + CLI (python -m eval.harness --out eval_report.json): all four methods over all 10 tasks, bootstrap 95% CI (seeded, 1000 resamples), misses list (tasks where cp_sat does not beat or tie the best baseline on role_coverage or robustness), table printed to stdout. Then docs/lanes/A-solver/EVAL_RESULTS.md containing the command and its REAL pasted output. Do not edit numbers by hand.
7. Property/adversarial tests (backend/tests/solver/): over 200 random seeds, cp_sat never violates a hard constraint (minor consent, availability, travel); cp_sat role_coverage >= nearest_skill role_coverage whenever baseline is itself feasible; deterministic with the same seed; solve under 10 s; forced_out respected.
